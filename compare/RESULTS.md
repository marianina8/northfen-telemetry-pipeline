# Naive fixed limits vs. adaptive windowed detection

Same synthetic scenarios, two deterministic detectors, no model involved. **Naive** uses the fixed spec-sheet
limits in `demo/equipment.yaml` (how most render-farm monitoring is configured). **Adaptive** is the pipeline's detector:
it learns each metric's own normal, then applies EWMA/z-score rules plus stuck and dropout checks. Cells show which metric
flagged and at which tick. Generated by `go run ./compare`.

**Naive: 5/10 correct. Adaptive: 10/10 correct.**

Where they differ:
- **Driver drift** (`04`): node12's frame time creeps up after its GPU driver update but never reaches the 14 min/frame alert limit, so the fixed limit never fires. The adaptive baseline moving 4σ from where it started does.
- **Bursty but healthy** (`06`): the expanded compositing pool mixes light and very heavy shots, so its frame time crosses the fixed limit within minutes even though nothing is wrong. That's a false alarm that trains wranglers to ignore alerts. The adaptive detector learns this pool's own swing.
- **Frozen license monitor / silent node** (`07`, `08`): a frozen or silent metric looks "within limits" to a fixed threshold. The adaptive detector treats both as monitoring faults.
- **Storage slowdown** (`10`): both catch it, but look at the order. The fixed limits page about two slow nodes first; NAS latency only crosses its own limit at tick 116, about 40 ticks later, so the first page points at the nodes. The adaptive detector flags storage latency first (tick 67) and both nodes within 8 ticks, and the pipeline groups all three into one alert whose diagnosis points at shared storage.
- **Threshold boundary** (`09`) isn't a fair fight. It's a hand-built fixture that pins the adaptive detector's exact z = 3.0 cutoff, well inside the alert limits by design. It's included so the table covers every fixture.
